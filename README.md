# 资源授权策略求值库

我们后台要给资源做细粒度授权。之前就是一张允许列表，谁要用就加一条，出过一次越权：一个人把自己某个目录的权限转手给了别人，结果对方连上层都拿到了。想自己写一个策略求值的库。

策略写法在下面：主体、资源路径、动作，路径支持前缀通配和单段通配，规则可以写允许也可以写拒绝。几条原则照那个来，别自己发挥：拒绝优先于允许；越具体的规则越优先；没有任何规则命中就是拒绝，别默认放行。委托链是这次的起因，要按下面那条约束做：把权限转给别人时只能收窄不能放大，转出去的不能超过自己手里的，链子长了几跳也得成立。被拒绝的时候要能说清楚是哪条规则拒的，命中多条的时候按优先级说最有分量的那条。性能上，几十万次判定要在一秒内完成，别每次把整份策略从头扫一遍。实现只用标准库，测试用 unittest。

仓库里只有这份说明和 samples 里的策略与请求样例，代码从零写。

## 策略文件

```json
{
  "rules": [
    { "effect": "allow", "subject": "alice", "path": "/team/**", "actions": ["read", "write"] }
  ],
  "delegations": [
    { "from": "alice", "to": "bob", "path": "/team/docs/**", "actions": ["read"] }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `rules[].effect` | `allow` 或 `deny` |
| `rules[].subject` | 主体标识（不区分？——**区分大小写**，字符串完全相等才算同一个主体） |
| `rules[].path` | 资源路径模式，见下一节 |
| `rules[].actions` | 动作名列表，请求动作必须在这个列表里才算命中（**没有动作通配**） |
| `delegations[].from` / `to` | 把 `from` 手里的权限转给 `to` |
| `delegations[].path` / `actions` | 转出的范围 |

规则的下标从 1 开始，按 `rules` 数组顺序数；委托的下标同理按 `delegations` 顺序数。这两个下标会出现在输出里。

## 路径语法与匹配

- 路径以 `/` 开头，段与段之间用单个 `/` 分隔（`/team/docs/x`）；根路径写作 `/`。
- `*` 匹配**恰好一段**，不跨层级：`/team/*/reports` 匹配 `/team/ops/reports`，不匹配 `/team/ops/2026/reports`。
- `**` 是**前缀通配**，只能出现在路径最后一段，匹配**零段或多段**：`/team/docs/**` 匹配 `/team/docs`、`/team/docs/a`、`/team/docs/a/b`。
- 路径比较**区分大小写**：`/Team/docs` 与 `/team/docs` 是两个不同的路径。
- 规则路径里除 `*`、`**` 之外的段都是字面量；匹配时逐段比较，字面量必须完全相等。

## 判定原则

对一次请求（主体、路径、动作），把所有命中的规则（含沿委托链继承来的）收集起来，按下面的顺序定结果：

1. **拒绝优先**：只要有命中的 `deny` 规则，结果就是拒绝；
2. **越具体越优先**：同一种效果里，先比路径的**非通配字符数**（多者更具体），再比**非通配段数**（多者更具体），还相同就比规则下标（小者优先）。命中的 `deny` 里最具体的那条决定拒绝原因；没有 `deny` 时，命中的 `allow` 里最具体的那条决定结果与原因；
3. **没有命中就是拒绝**：一条规则都没命中（也没有可用的委托来源）时，结果是拒绝，原因是 `no-rule`。

具体度只用于「同效果内部」和「拒绝优先之后的 reason 选择」，不会让一条更具体的 `allow` 推翻 `deny`。

## 委托规则

委托是「把 `from` 手里的某段允许权限转给 `to`」，约束是**只能收窄不能放大**：

1. 转出的 `path` 与 `actions` 必须被 `from` **自己实际持有**的某条 `allow` 完全覆盖（`from` 自己的规则，或沿更上游的委托继承来的、并且把链上每一跳的收窄都算进去）；
2. 覆盖判定（路径包含）：把 `outer`（手里那条）与 `inner`（要转出的）按段比——`outer` 以 `**` 结尾时，`inner` 的段数不少于 `outer` 的前缀段数，且逐段满足「`outer` 的 `*` 可以覆盖 `inner` 的任意一段；否则两段必须字面相等」；`outer` 不以 `**` 结尾时，两者段数必须相同，逐段同样规则。`inner` 里出现 `*` 或 `**` 的位置，只有 `outer` 在同段是 `*` 时才允许；
3. **逐条按声明顺序校验**：检查第 i 条委托时，「自己手里有什么」只算已经判定合法的委托；
4. 非法委托**不生效**（既不能用来继承，也不能用来继续往下转），并在输出里记一行 `invalid-delegation,<委托下标>,too-broad`；
5. 链子长几跳都按同一套规则验：`alice → bob → carol`，carol 拿到的是「alice 的规则 ∩ 第一跳范围 ∩ 第二跳范围」。

拒绝规则不参与委托：委托只转移允许；`deny` 只在求值时按优先级生效。

## 其它口径

- **空策略**（没有规则、也没有委托）：任何请求都是拒绝，原因 `no-rule`。
- **资源是否存在**不影响判定：求值只看策略与请求里的路径字符串，不去查资源树。
- 请求里的路径必须已规范化（不带 `//`、`.`、`..`、末尾 `/`），策略也按同样约定书写；不规范化就直接按字符串段比较。
- 同一份策略与同一批请求，跑两遍输出必须逐字节一样。

## 输出格式

先按委托顺序输出非法的委托（如果有），再按请求顺序输出判定，每行逗号分隔、行尾 LF：

```text
invalid-delegation,<委托下标>,too-broad
<请求编号>,<allow|deny>,<reason>
```

`reason` 的取值：

| 取值 | 含义 |
| --- | --- |
| `rule:<规则下标>` | 命中的那条规则（`allow` 时是最具体的允许规则，`deny` 时是最具体的拒绝规则） |
| `no-rule` | 没有任何规则命中，也没有可用的委托来源 |

## 性能要求

- 几十万次判定要在 **1 秒**内完成（单线程、只算求值本身）；
- 不许每次判定都把整份策略从头扫一遍：至少要按主体分桶，主体内部再按路径段做前缀索引或同样量级的结构；委托链的展开结果可以缓存，但要保证缓存不改变判定结果。

## 样例

```text
samples/policy-1.json / requests-1.csv / expected-1.txt    小策略：deny 优先、具体优先、两种通配、两跳委托、两条非法委托
samples/policy-2.json / requests-2.csv / expected-2.txt    1000 条规则 + 1500 条请求，用来压性能与确定性
samples/policy-3.json / requests-3.csv / expected-3.txt    空策略：全部 no-rule
```

case-1 里几个关键点：同一条路径上 `allow` 与 `deny` 并存时按拒绝优先；`carol` 通过两跳委托继承到权限，但链条之外的范围仍然拒绝；`dave`、`erin` 对应的委托因为转得比手里宽而判为非法，请求一律 `no-rule`；`/Team/docs/x` 因为区分大小写被拒。

## 实现说明

代码在 `policy_engine.py`（库 + 命令行），测试在 `test_policy_engine.py`（unittest）。

### 运行方式

```bash
python3 policy_engine.py <policy.json> <requests.csv>   # 结果写 stdout
python3 -m unittest                                     # 跑全部测试（含样例逐字节比对）
```

### 索引结构

- 规则按**主体分桶**：每个主体一个索引，内部再按路径模式**首段字面量**分桶；首段是 `*`/`**` 或空模式（`/`）的进通配桶。判定一次请求时，只用请求路径首段取一个字面量桶加通配桶，绝大多数规则在桶这一层就被排除，不做逐条扫描。
- 每条规则在加载时预编译：路径切成段元组、动作转 `frozenset`、具体度（非通配字符数、非通配段数）算好存下，求值时只做整数比较。
- 求值结果按 `(subject, path, action)` 记忆化；策略构造后不可变，缓存不影响结果，重复请求是 O(1)。

### 委托链的校验与展开

- 构造时按声明顺序逐条校验委托：维护每个主体「实际持有的允许范围」列表（自己的 allow 规则 + 已判合法的委托继承），新委托的 `path`/`actions` 必须被其中**某一条**完全覆盖（路径包含按「委托规则」第 2 条的逐段规则，动作是子集关系），否则记 `invalid-delegation` 且不生效、不参与后续校验。
- 校验通过只做一件事：在受让方的「入边委托」列表里记一条 `(范围, 动作, 来源主体)`。不做全链展开，因此不存在链式展开的缓存一致性问题。
- 求值时沿入边委托走图：请求落在某跳范围内（路径命中且动作包含）才把来源主体入栈继续收集，用 visited 集合防环。整条链上所有命中的规则（含来源主体的 `deny`）汇到一个池子里，统一按「拒绝优先、同效果比具体度」结算——所以多跳的收窄天然成立，且来源的拒绝规则在委托范围内对受让方生效。

### 单次判定复杂度

设该主体首段命中的候选规则数为 `k`（分桶后通常是个位数）、有效入边委托数为 `d`、路径段数为 `m`：单次未命中缓存的判定是 **O((k + d) · m)**，与策略总规则数无关；命中结果缓存是 O(1)。实测：1500 条规则 + 72 条委托的策略，30 万次全不重复判定约 0.37s（单线程，仅求值），有重复时约 0.04s。
